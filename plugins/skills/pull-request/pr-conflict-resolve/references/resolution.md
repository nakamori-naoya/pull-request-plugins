# 意味を保つ競合解消

## 解消結果が使われる場面

競合解消結果は、PRの変更目的をbaseの最新契約へ接続し、reviewとtestで検証できるbranchとして使われる。markerが無くても、base側の不具合修正やhead側の到達目標が失われていれば未完了である。両側の意図を、統合後の具体的な入力・出力・副作用で説明できる実装を選ぶ。

典型例では、base側が例外時のcleanupを追加し、head側が処理を非同期化している。左右のblockを連結するだけでなく、非同期の成功・失敗経路でもcleanupが一度だけ動くように組み直し、関連testで確かめる。

## 似ているが不十分な解消

`ours`または`theirs`の一括採用、marker削除だけの手編集、最新commit側の無条件優先は解消方針にならない。どちらか一方が正しい場合も、反対側の目的が不要・別箇所で充足・誤りのいずれかを根拠で説明する。

format差だけに見える競合でも、近接する条件分岐や設定値が変わっていないか確認する。反対に、Gitが競合と判定しない自動merge部分も、同じ契約を両側が変更しているなら統合diffとして確認する。

## 境界事例

delete/modifyでは、削除が機能廃止なのか移動なのか、変更が残すべき互換性修正なのかを追う。移動先へ変更を移植する場合は、旧fileを復活させない。

lockfile、生成code、snapshotは入力側を先に統合し、repositoryが定める生成commandで作り直す。再生成が広い無関係差分を生む場合は原因を分け、対象外差分を混ぜない。

両側のゴールが同時に満たせない場合は、片側を推測で捨てない。衝突する受入条件、選択肢、影響範囲を示して停止し、利用者または仕様所有者の決定を待つ。

調査後にbaseまたはheadが更新された場合は、以前の結論を流用しない。競合集合と関連実装を取り直し、同じ根拠がまだ成立するか確認する。
