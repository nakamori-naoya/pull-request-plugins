# 競合から実装意図を復元する

## 実際の使われ方

競合調査は、markerの左右から残す行を選ぶ作業ではない。PRを作る人が、base側で守られてきた契約とhead側が達成しようとする変更を同時に満たす実装を選ぶために使う。対象行の前後だけでなく、呼び出し元、test、設定、生成元、公開APIまで読み、両側の変更が利用者へ届く経路を説明できる状態にする。

典型例は、同じ関数へbase側が入力検査を追加し、head側が戻り値を変更した競合である。正しい問いは「どちらの行を残すか」ではなく、「新しい戻り値を保ちながら、追加された入力契約も満たせるか」である。関連commitとPR本文・reviewを読み、各変更の目的と受入条件を確かめる。

## 似ているが競合調査ではないもの

mergeが成功するのにtestが失敗する状態は統合不具合であり、Git競合そのものではない。競合なしと記録したうえで別の修正課題として扱う。反対に、markerが単純でも、一方が削除し他方が変更したdelete/modifyは意図が正反対かもしれず、機械的に片側を選ばない。

lockfileや生成物の競合は「生成物だから片側を採る」で終えない。入力となるmanifestやschemaの両側の変更を統合し、正規の生成commandで再生成する方針を候補にする。生成元が不明なら確定扱いしない。

## 判断が分かれる境界

片側の変更が後発でも、後発というだけでは優先しない。後発修正が既知不具合を直したのか、別目的の一時回避なのかを関連commit、issue、PR review、testで判定する。過去PRが見つからない場合も「履歴なし」と「取得不能」を区別する。

同名symbolの履歴だけでは足りない場合がある。rename、file移動、呼び出し側の変更を追い、必要なら`git log --follow`や関連語で範囲を広げる。ただし無関係なrepository全史を要約せず、競合する契約とゴールを説明する証拠へ絞る。

新しい事例で両側の目的を説明できないときは、解消案を先に作らない。対象範囲、履歴、PR、testのどこが欠けているかを特定し、調査を広げるか停止理由として返す。
