# resolve-pr-conflicts

競合の解消は、marker の左右から残す行を選ぶ作業ではない。base 側で守られてきた契約と、head 側が達成しようとする変更を、同時に満たす実装を選ぶ作業である。だから、両側の意図を復元してから解く。

## 両側の意図を、証拠から復元する

競合した行の前後だけでなく、base、head、共通祖先の実装と、呼び出し元、test、設定、生成元、公開 API を読む。関係する commit、blame、issue、過去の PR の本文と review から、それぞれの変更の目的と受入条件を取り出す。rename やファイルの移動は `git log --follow` で追う。ただし無関係な履歴の要約には広げず、競合する契約と目的を説明する証拠に絞る。PR を取得できなかったときは「履歴が無い」と「取得できない」を分け、代わりに確かめた履歴を書く。

典型は、同じ関数に base 側が入力の検査を足し、head 側が戻り値を変えた競合である。問うべきは「どちらの行を残すか」ではなく、「新しい戻り値を保ったまま、足された入力の契約も満たせるか」である。

## 片側の一括採用で解かない

`ours` や `theirs` の一括採用、marker を消すだけの手編集、後から入った側の無条件の優先は、解消の方針にならない。一方だけが正しいときも、反対側の目的が不要なのか、別の場所で満たされているのか、誤りなのかを根拠で説明する。

delete/modify は意図が正反対のことがある。削除が機能の廃止なのか移動なのかを追い、移動なら変更を移動先へ移し、古いファイルを復活させない。lockfile、生成コード、snapshot は、入力の側（manifest や schema）を先に統合し、repository の生成 command で作り直す。Git が競合と判定しなかった部分でも、両側が同じ契約を変えていれば統合の diff として確かめる。

解消は、base を作業 branch へ merge する形で行う。rebase で履歴を書き換えない。解いた後は、unmerged の entry と競合 marker が残っていないこと、解消の diff が復元した目的と合うことを確かめ、repository が完了判定に使う検証を通す。検証の command は、作業方針の設定の `verification.commands` を記載順にすべて実行する。設定は、repository が自分の `.harness-plugins/agent-work-policy.config.yml` を持っていればその一つだけを読み、持っていなければ `/Users/naoya-nakamoriq/Documents/Github/harness-pluginsv2/.harness-plugins/agent-work-policy.config.yml` を読む。二つを重ねて上書きしない。どちらも無ければ、検証を推測で選ばずに止まる。

## 止まるか、仮説で進むかは、方針が変わるかで決める

両側の目的を同時に満たせないときは、片側を推測で捨てない。衝突する受入条件、選択肢、影響範囲を示して止まり、利用者か仕様の持ち主の決定を待つ。

調査を広げても復元できない目的があるときは、欠けた情報が解消の方針を変えるかで分ける。どう埋まるかで残す振る舞いや組み合わせ方が変わるなら、止まって、方針が分かれる選択肢と決めるのに要る情報を返す。どう埋まっても方針が変わらないなら、欠けている範囲を明示し、方針を仮説として書いて進む。

調べている間に base か head が進んだら、以前の結論を流用しない。競合の集合と関連する実装を取り直し、同じ根拠がまだ成り立つかを確かめる。

解消の前に方針を見せてほしいと利用者が頼んでいれば、競合、両側の目的、推奨する方針を示して承認を待つ。頼まれていなければ解いてから、起きていた競合、採った方針、検証の結果を報告する。解いた branch は push も PR もしないまま返す。
